# Архитектура PC MATE

Документ объясняет, из чего состоит система и почему решения приняты именно так.
Контракт обмена данными — в [protocol.md](protocol.md).

---

## 1. Общая схема

```
    ┌──────────────┐        HTTPS / WebSocket        ┌──────────────────┐
    │   Телефон    │ ──────────────────────────────► │ Сервер-ретранс-  │
    │  (Android)   │ ◄────────────────────────────── │ лятор (VPS)      │
    └──────┬───────┘                                 └───────┬──────────┘
           │                                                 │
           │ UDP 9 (магический пакет),                       │ WebSocket
           │ WebSocket в домашней сети                       │
           │                                                 │
           │                                    ┌────────────▼─────────┐
           │                                    │  Мост пробуждения    │
           │                                    │  (ESP32 / RPi)       │
           │                                    └────────────┬─────────┘
           │                                                 │ UDP 9
           ▼                                                 ▼
    ┌──────────────────────────────────────────────────────────────────┐
    │                       Компьютер (Windows)                        │
    │  ┌────────────────────────┐        ┌──────────────────────────┐  │
    │  │ Служба (SYSTEM)        │◄──────►│ Помощник в сеансе        │  │
    │  │ Session 0              │  канал │ пользователя (трей)      │  │
    │  │ питание, расписания,   │        │ окна, запуск программ,   │  │
    │  │ сеть, криптография     │        │ громкость, QR, мастер    │  │
    │  └────────────────────────┘        └──────────────────────────┘  │
    └──────────────────────────────────────────────────────────────────┘
```

## 2. Почему агент состоит из двух частей

Служба Windows работает в **Session 0** — изолированном сеансе без рабочего
стола. Оттуда можно управлять питанием и Планировщиком, но нельзя ни открыть
окно, ни запустить программу так, чтобы её увидел пользователь.

Поэтому агент разделён:

| | Служба `PcMate.Agent.Service` | Помощник `PcMate.Tray` |
|---|---|---|
| Запуск | автоматически, от `SYSTEM` | при входе пользователя, от него же |
| Права | полные (powercfg, реестр, Планировщик) | обычные |
| Делает | питание, таймеры, расписания, связь, шифрование | окна, запуск программ, громкость, список приложений |
| Живёт | всегда | пока пользователь в системе |

Связь между ними — именованный канал `\\.\pipe\pcmate-session` с JSON-строками
(`PcMate.Core.Ipc.PipeLink`). Канал двунаправленный: служба просит помощника
выполнить шаг сценария, помощник просит службу выполнить команду протокола,
когда пользователь жмёт кнопку в трее. Обе стороны ходят через один и тот же
`CommandDispatcher`, поэтому поведение кнопки в трее и кнопки в телефоне
одинаковое по определению.

Права на канал выданы явно: `Authenticated Users` — чтение и запись,
администраторы и `SYSTEM` — полный доступ.

## 3. Два пути от телефона к компьютеру

Телефон умеет разговаривать с агентом двумя способами, и оба используют
**одно и то же сквозное шифрование**:

1. **Локальная сеть.** Агент поднимает `HttpListener` на порту 8760:
   `/health`, `/pair/claim`, `/ws`. Телефон сначала проверяет `/health` по
   сохранённым адресам ПК и, если компьютер отвечает, работает напрямую.
   Интернет и сервер при этом не нужны совсем.
2. **Сервер-ретранслятор.** Агент держит исходящее WebSocket-соединение с
   сервером. Это важно: на домашнем роутере **не нужно открывать ни одного
   порта** — соединение инициирует сам компьютер.

Выбор канала (`PcConnection.pickTarget`) по умолчанию: сначала локальная сеть
(быстрее и работает без интернета), потом сервер. Переключается в настройках.

## 4. Включение компьютера: три сценария

| Ситуация | Что происходит |
|---|---|
| Расписание «включить в 23:00» | Агент заранее создал задачу в Планировщике с `WakeToRun`. Windows будит компьютер по аппаратному таймеру. **Сеть не нужна.** |
| Телефон дома, ПК спит | Телефон сам шлёт магический пакет на широковещательный адрес подсети (UDP 9 и 7, три повтора). |
| Телефон не дома | Телефон просит сервер, сервер просит мост, мост шлёт пакет изнутри домашней сети. |

После отправки пакета инициатор ждёт до 90 секунд события `agent.hello` или
`power.wake`. Не дождался — показывает диагностику и ссылку на мастер готовности.

**Почему нужен мост.** Магический пакет — это UDP-датаграмма на
широковещательный адрес. Маршрутизаторы её не пересылают, а проброс порта на
роутере для WOL работает ненадёжно (ARP-запись выключенного ПК истекает).
Поэтому единственный честный способ включить ПК снаружи — устройство внутри
сети. ESP32 стоит около 500 ₽ и потребляет доли ватта.

## 5. Как агент узнаёт, что компьютер проснулся

`PowerEventWatcher` раз в 5 секунд сравнивает **настенные часы** и
**системный счётчик тиков** (`GetTickCount64`). Во сне тики не идут, а часы
идут. Расхождение больше 25 секунд означает, что компьютер спал.

Приём простой, но у него есть важное достоинство: он работает одинаково и в
службе, и в консольном режиме, и не требует ни оконного цикла сообщений, ни
подписки на `SystemEvents` (которые в Session 0 ненадёжны).

Причину пробуждения агент берёт из `powercfg /lastwake`.

## 6. Расписания: почему их две копии

Расписание хранится **и на компьютере, и на сервере**:

* на компьютере — потому что исполняет их агент, и «включить» обязано работать,
  когда сервера нет (задача уже лежит в Планировщике Windows);
* на сервере — потому что телефон должен видеть и править расписания, даже
  когда ПК выключен, а после переустановки агента они должны вернуться.

Признак `synced = syncedAt >= updatedAt` показывает, успел ли агент завести
задачу. Телефон рисует ⏳, пока подтверждения нет.

Задачи Планировщика создаются через `schtasks /Create /XML` с флагом
`<WakeToRun>true</WakeToRun>`. Действие задачи — запуск агента с ключом
`--fired <id>`: короткий процесс кладёт файл-триггер в `%ProgramData%\PcMate\triggers`
и выходит. Служба подхватывает файл в своём цикле.

Почему через файл, а не напрямую: сразу после пробуждения службы и сеть ещё
поднимаются, и попытка достучаться до службы в этот момент — гонка. Файл
переживает любые задержки и не теряется.

## 7. Сервер-ретранслятор

Node.js + Fastify + `ws` + SQLite (better-sqlite3). Задача у него ровно одна:
**передать конверт от одного спаренного устройства другому**.

* Аутентификация — bearer-токен устройства; в базе хранится только SHA-256.
* `from` в конверте всегда переписывается идентификатором из соединения —
  представиться чужим именем нельзя.
* Маршрут проверяется по таблице пар: несопряжённым устройствам сервер
  отказывает (`route.fail` с причиной `denied`).
* Незашифрованные `cmd`/`res`/`evt` отбрасываются: сервер не станет пересылать
  то, что смог бы прочитать.

Сервер разворачивается одной командой (`docker compose up -d`), TLS получает
Caddy автоматически.

## 8. Криптография

```
X25519(phonePriv, pcPub) ──► shared
HKDF-SHA256(shared, salt = pairId)
        ├─► ключ «телефон → ПК»
        └─► ключ «ПК → телефон»
AES-256-GCM(ключ, nonce 12 байт, AAD = маршрутные поля)
```

Направленные ключи означают, что перехваченное сообщение нельзя «отразить»
обратно отправителю. AAD связывает шифротекст с `v|id|from|to|ts` — сервер не
может подменить получателя или время, не сломав проверку тега.

Три независимые реализации (C# на BouncyCastle+`AesGcm`, TypeScript на
`@noble`, Python/JS на `node:crypto`) сверяются с общими тестовыми векторами
([test-vectors.json](test-vectors.json)) в CI.

## 9. Устойчивость

| Что ломается | Что происходит |
|---|---|
| Сервер недоступен | Локальный режим продолжает работать; расписания «включить» тоже — они в Планировщике |
| Служба упала | Windows перезапускает её (`sc failure ... restart/5000`) |
| Помощник закрыт | Питание и расписания работают; сценарии сообщают «нет сеанса пользователя» |
| Интернет пропал | Агент переподключается с экспоненциальной задержкой до 60 с |
| Windows сбросила настройки питания после обновления | Агент перепроверяет готовность при каждом старте и пишет предупреждения в журнал |
| Телефон не в домашней сети | Включение уходит через мост; если моста нет — приложение честно объясняет, почему не получится |

## 10. Выбор технологий

| Компонент | Что выбрано | Почему |
|---|---|---|
| Агент | C# / .NET 8 | Лучший доступ к Windows API (питание, Планировщик, DPAPI, именованные каналы) без внешних зависимостей |
| QR на ПК | QRCoder | Чистый managed-код, без нативных библиотек |
| X25519 | BouncyCastle | В BCL .NET 8 X25519 нет; BouncyCastle — один managed-DLL без нативных зависимостей |
| Сервер | Node.js + Fastify | Быстрый старт, один процесс на HTTP и WebSocket, разворачивается в Docker одной командой |
| Хранилище | SQLite | Данных мало, резервная копия — один файл; PostgreSQL избыточен для домашнего сервера |
| Приложение | React Native + Expo | Одна кодовая база под Android и iOS, богатая экосистема модулей |
| Криптография на телефоне | `@noble/*` | Чистый JS, не требует нативной сборки, аудирован |
| Мост | ESP32 / Python | ESP32 — 500 ₽ и доли ватта; Python — если дома уже есть Raspberry Pi |
